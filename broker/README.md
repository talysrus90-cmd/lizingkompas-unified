# Compass Broker Core — P0, изолированный прототип

**Статус: offline/synthetic, не развёрнут, не подключён к публичной V5.**
Это код для проверки бизнес-правил, а не работающий личный кабинет или SaaS. Никаких персональных данных, реальных документов, токенов, запросов к лизинговым компаниям или сайтов операторов.

## Что уже можно проверить
- `access_policy.py`: решения «разрешено / запрещено» по роли, организации и назначенной сделке. Проверка авторизации не заменяет аутентификацию.
- `case_workflow.py`: карточка сделки в оперативной памяти, назначение через допущенного руководителя, состояния draft -> collecting -> comparing -> closed, атомарные проверки версии и неизменность прочитанного экземпляра.
- `offer_comparison.py`: 2–20 КП, ссылка-идентификатор на исходный документ (без хранения документа), верификация брокером, одинаковые объект/аванс/срок/НДС, дата действия, учёт всех **явно известных** расходов; неполные КП отображаются без рейтинга. Это сумма денежных выплат **без дисконтирования** и без расчёта налоговой выгоды / эффективной ставки.
- `demo.py`: искусственные данные трёх лизингодателей, полный прогон без записи на диск или обращения к сети.

## Запуск проверки
Нужно: **Python 3.11+**, только стандартная библиотека.
Из корня репозитория:
```bash
python -m unittest discover -s broker -p 'test_*.py' -v
python broker/demo.py
```

## Ограничения и релизные запреты
1. Текущие `Actor` создаются тестами. Реальная авторизация требует серверной аутентификации с MFA, проверенных ролей, и назначений только из доверенной БД. Не использовать `Actor`, сформированный из JSON браузера.
2. `CaseDesk` работает **только в RAM**; после перезапуска всё пропадает. Никакого хранения клиентов, журналов аудита, резервных копий, защищённых сессий или API **нет**.
3. Исходные КП *не сохраняются*, только `source_document_id`. Для продукции нужны закрытое хранилище с карантином/антивирусом, версия документа и проверка вручную.
4. Поля комиссий/страхования обязательны для рейтинга: неизвестные суммы = `None` и отсутствие ранга. Стандартная схема платежей используется только при фактическом наличии равного ежемесячного платежа. Нет сложных графиков, индексации, НДС и скидок.
5. Нельзя подставлять рыночные условия или ставки из интернета как реальные КП и нельзя собирать КП из чужих закрытых кабинетов без разрешения.
6. Нельзя подключать публичную форму, Telegram/MAX, email, поисковую индексацию или персональные данные в этой ветке. `variant-5.html` не меняется.
7. Этап `closed` требует назначенного supervisor, назначение команды в прототипе выполняет только уже назначенный supervisor; организационное управление членством и сложные полномочия — отдельная задача.
8. Безопасная серверная эксплуатация потребует БД в РФ, RBAC/ABAC на каждом endpoint и поле, недоверия к входным версиям, журналирования, защиты входа и загрузок, тестирования отказов, договора на ПД, согласований.

## Последующие этапы
- Отдельный защищённый backend и операционная очередь для Secure Intake; POST не активировать до юридического и инфраструктурного допуска.
- Схема PostgreSQL, модель назначений и журнал неизменяемых событий, идемпотентность, конкурентные блокировки.
- Импорт документа -> OCR только с проверкой человеком -> извлечённые поля/ссылка на оригинал -> сравнение, затем Legal, Verify, Analytics, Connect.
- Полные графики платежей и точное приведение к единому сценарию с пометкой допущений.
- Работающий отдельный кабинет брокера после тестов входа, mobile/desktop и прав; публичную V5 не перегружать.

## Локальная SQLite-база для синтетических сделок (P0.1)
- `broker/sqlite_store.py`: транзакционная запись заявки, назначения брокера, КП и этапов; отдельная таблица событий с идентификаторами и версиями; проверка tenant/case/role на серверной модели; атомарный контроль конкурентных изменений.
- `broker/test_sqlite_store.py`: автотесты восстановления после закрытия и повторного открытия базы, чужих сделок, дубликатов оригиналов, версий, журналирования и прав доступа.
- `broker/sqlite_demo.py`: полностью временная база с синтетическими данными; создаётся в каталоге ОС для временных файлов и удаляется после завершения.
- Для запуска нужны **Python 3.11+ и только стандартная библиотека**. Дополнительно выполнить `python broker/sqlite_demo.py`.
- CI проверяет весь набор брокерских тестов **на Linux и Windows**; все сценарии остаются offline.
- SQLite-файл **не предназначен для хранения реальных персональных данных**: без серверной аутентификации, отдельной защищённой операторской очереди, управления ключами, резервирования и удаления по срокам использовать нельзя.
- Аудит здесь только обычная таблица SQLite, а не криптографически защищённый/неизменяемый журнал. При выборе production backend предпочтительна PostgreSQL в РФ и отдельное хранилище защищённых аудиторских событий.
- `Actor` в тестах создаётся искусственно. Права и назначение пользователей для production должны происходить из доверенной БД полномочий после идентификации, проверки членства в организации и MFA. **Не принимать роли/tenant/назначения из браузера**.
- Для Windows test-фикстуры явно закрывают соединения перед удалением временной базы.
