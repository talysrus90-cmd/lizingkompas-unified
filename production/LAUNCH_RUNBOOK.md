## Что реализуется этим пакетом
1. Django 5.2 LTS, PostgreSQL, Gunicorn и Caddy (автоматический TLS), независимый от статического сайта backend.
2. /apply/ — серверная заявка с CSRF, отдельным явным согласием, обязательной версией согласия, проверкой формы, ограничением частоты, идемпотентностью формы и шифрованием контактных полей (Fernet).
3. /callback/ — отдельная защищённая форма заказа обратного звонка с минимальным набором данных и отдельным согласием; запрос появляется в закрытой очереди оператора. /admin/ — закрытая внутренняя CRM со списком заявок, назначением ответственных, этапами, контактами, контрольным журналом и двумя–двадцатью коммерческими предложениями для сравнения **при наличии исходных КП**. Публичный Caddy отдаёт на /admin/ **404**; доступ оператору только по SSH-туннелю.
4. PostgreSQL с приватной Docker-сетью, URL без утечки ключей, постоянные тома и проверки состояния.
5. По умолчанию `COMPASS_LIVE_INTAKE=no`; при недостаточных ключах, договорных/правовых/резервных подтверждениях backend **не запустит приём заявок**.
6. Файлы клиентов, паспорта, OCR, реальный MAX, БКИ, ЭП и автоматический запрос КП **не подключены**. Их нельзя имитировать фиктивными ответами.

## Безопасное размещение (не запускать без необходимых доступов)
- Выбрать **российский VPS** и подтвердить физическое расположение БД, томов и backup в РФ. Selectel предлагает PostgreSQL в своих ЦОД в РФ, Timeweb Cloud имеет российские регионы — конкретный регион и договор должны быть подтверждены при заказе.
- На VPS установить Linux, Docker Compose, SSH по ключам, запретить парольный SSH и root login, настроить firewall: только 22/80/443; журналы, обновления, защиту от входа, отдельные учётные записи и мониторинг.
- Сформировать на сервере секреты отдельно. Никогда не присылать их в чат и не помещать в Git:
  - Django SECRET_KEY длиной от 50 символов.
  - PostgreSQL DB_PASSWORD (в URL символы должны быть URL-encoded).
  - `COMPASS_FERNET_KEYS`: Fernet key 32 байта, сгенерированный в безопасном терминале (пример `python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"`). Хранить независимую защищённую копию ключей для восстановления и ротации.
  - Отдельный HMAC throttle secret длиной 32+ символа.
- Заполнить `production/.env.production` из `production/.env.production.example` только на сервере, `chmod 600`. Настроить `PRIMARY_DOMAIN`, DNS A/AAAA и www, SSL; **не менять MX/TXT почты при настройке сайта**.
- После утверждения политики и проверки фактического уведомления РКН заполнить `COMPASS_CONSENT_VERSION`; отдельно согласовать текст согласия, политику, сроки хранения/удаления, договор с хостером и назначение ответственного за ПД.
- Сборку публичного сайта делать во внешнем каталоге /srv/leasingcompass/site-public (не внутри репозитория, чтобы не попасть под контроль Git) отдельно от preview, чтобы не индексировать учебные страницы и не перезаписать V5: `python seo/prepare_release.py --output /srv/leasingcompass/site-public --confirm-ready` **только после технической готовности**. Проверить, что корневой / показывает **утверждённую V5**. Статическую копию публиковать через Caddy и проверить все изображения/ссылки.
- В `production/` на VPS выполнить `docker compose --env-file .env.production -f docker-compose.prod.yml config -q`. До смены DNS протестировать через hosts-файл или staging-домен и SSL.
- Выполнить миграции: `docker compose --env-file .env.production -f docker-compose.prod.yml exec app python manage.py migrate --noinput`.
- Создать операторский аккаунт `createsuperuser` ТОЛЬКО после защиты SSH. Админка запущена **отдельным приватным процессом** `operator` на 127.0.0.1:8002 (публичное приложение остаётся HTTPS-only и не делит cookie с оператором). Открыть туннель `ssh -L 8002:127.0.0.1:8002 user@your-server` и браузер `http://127.0.0.1:8002/admin/`. Через SSH трафик шифруется, а публичный прямой URL /admin/ обязан отдавать 404. Для команды внедрить отдельный MFA и раздельные роли до распределения доступов.
- Перед включением живых заявок провести инфраструктурное тестирование отказов, backup/restore, проверки подбора паролей, rate limiting, XSS/CSRF, контроля доступа, headers и журналирования; определить срок хранения согласий и обращений, процедуру удаления по законному запросу.
- После положительного контрольного акта установить все разрешающие переменные, затем включить `COMPASS_LIVE_INTAKE=yes`. **Не включать флаги на основании одного только запуска тестов.**
- После запуска переключить сайт на основной домен; альтернативные домены 301; включить индексирование лишь в утверждённой production-сборке, подключить Yandex Webmaster / Search Console / IndexNow, регулярно проверять доступность/лиды/резервирование.

## Резервирование и восстановление
- На хостинге РФ создать **зашифрованный restic-репозиторий**, отдельный ключ и парольный файл (chmod 600). Выбрать совместимое приватное хранилище **только в РФ**; не использовать пользовательские фото/документы в иностранном облаке.
- Планировать `production/ops/backup.sh` через systemd timer/cron; он потоком передаёт PostgreSQL custom-format в restic, **без временного незашифрованного dump-файла**. Проверяет репозиторий через `restic check`.
- Проводить `production/ops/restore_drill.sh` только в свежую независимую БД с именем restore_test; восстановление и проверка таблиц обязательны до `COMPASS_RESTORE_TEST_PASSED=yes`.
- Тестовый запуск сам по себе НЕ выполняет реальное резервное копирование и не подтверждает восстановление: хостинг, доступы, репозиторий, расписание и ключи требуют реальной инфраструктуры.

## Обязательная проверка до реального запуска
`python production/ops/preflight.py --env production/.env.production --site /srv/leasingcompass/site-public --require-live` формирует отчёт о DNS/HTTPS, запрете публичного /admin/, наличии production-V5, юридической политике, реестре РКН, ключах и восстановлении. **Зелёный отчёт не заменяет независимую оценку безопасности и юридическое утверждение**; тест нужно выполнять на реальном сервере после подключения DNS.

**Особенно важно:** текущие `privacy.html` и `consent.html` содержат заметку «Проект для согласования с оператором» и неуточнённый адрес ИП. Это не окончательные юридические документы. Нельзя делать `COMPASS_POLICY_APPROVED=yes` или запускать приём ПД до их утверждения оператором и проверки записи РКН.

На этапе pilot заявка персональных данных оформляется в **единой защищённой форме /apply/**; все четыре старые отключённые формы предпросмотра в production-сборке заменены соответствующими CTA. Кнопка обратного звонка использует **/callback/**. Таким образом, только серверные формы могут принимать ПД, а расчёты/галерея/публичная V5 продолжают работать по утверждённому дизайну.

Серверная CRM реализует назначение заявки сотруднику: суперпользователь назначает брокера, брокер с ограниченными правами видит только свои заявки. Обратные звонки доступны только суперпользователю. Изменение статуса, исполнителя, добавление/редактирование/удаление КП фиксируются в операторском журнале. Это первая рабочая CRM; OCR, БКИ, согласование графиков и финансовые API не следует выдавать за подключённые.
