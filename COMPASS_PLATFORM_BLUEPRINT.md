# Compass Platform — архитектура закрытого брокерского кабинета
Дата: 2026-11-27. Статус: проектное решение / план реализации, **НЕ означает работающие интеграции**.

## Неприкосновенная база V5
- Production/preview entry point V5: `variant-5.html?v=508`; основной `main`, защита `stable/v5.08`.
- Варианты страниц, мобильная шапка, калькулятор, формулы, публичные сценарии и постоянная ссылка остаются без изменений.
- GitHub Pages предназначен исключительно для публичной статической демонстрации. Никакие заявки, токены, документы клиентов или приватный кабинет на GitHub Pages не размещать.
- До отдельного согласования: `noindex,nofollow`, формы демонстрационные, внешние отправки запрещены.
- Подготовленные, но не включённые PR: #1 SEO Engine (feature/seo-engine-v1); #2 Secure Intake (feature/secure-intake-v1). Не сливать автоматически.

## Рекомендуемая целевая схема
```text
Публичный V5 (статика, без ПД) -------+
                                      |-> HTTPS / API Gateway / BFF (РФ)
Закрытый кабинет брокера (отдельный) -+      |
                                             +-- Identity + MFA + RBAC/ABAC
                                             +-- CRM / Cases / Offers / Documents
                                             +-- Compliance + Audit / Events
                                             +-- Adapter Hub (партнёры, MAX, CRM, реестры)
                                             +-- Job queue (OCR/AI/market monitoring)
                                             +-- PostgreSQL (РФ) + закрытое объектное хранилище (РФ)
Администратор -> отдельная защищённая админ-поверхность, без общедоступной ссылки на секретные API
```
**Старт: модульный монолит**, а не 14 микросервисов. Логические границы и версии API с первого дня; вынести OCR/AI/сканеры в фоновые workers по нагрузке. Минимум технологий: Python 3.12 + FastAPI/Pydantic или современная поддерживаемая альтернатива, PostgreSQL, очередь задач с повторными попытками и идемпотентностью, приватное S3-совместимое хранилище в РФ. Выбор конкретного провайдера и стоимость не утверждены. Не использовать личный ПК как сервер.

## Поверхности интерфейса
1. Публичный сайт — калькулятор, описание реальных услуг, примеры, контакты, добровольное обращение **только после разрешённого запуска Secure Intake**.
2. Брокер — карточка клиента и сделки, входящие заявки, сравнение реально полученных КП, проверка, договоры, документы, поиск имущества, господдержка, задачи, аналитика; без технических настроек и ключей.
3. Администратор — пользователи/роли, безопасность, источники, интеграции, наблюдаемость, лимиты AI, журнал изменений, Evolution, политика хранения и инциденты.
4. Клиент — **отдельная будущая фаза**, только ограниченное чтение собственной заявки/договора после проверки полномочий. Не путать с брокерским кабинетом.

## Модель данных: основной минимум
- `users`, `roles`, `role_grants`, `sessions`, `organizations`, `memberships`.
- `leads`, `cases`, `tasks`, `consent_receipts`, `contact_history`.
- `lessors`, `offers`, `offer_revisions`, `offer_sources`, `comparisons` (не изменять оригинал КП).
- `documents`, `document_versions`, `ocr_extractions`, `legal_findings`, `review_decisions`.
- `assets`, `suppliers`, `price_observations`, `verification_checks`, `subsidy_programs`.
- `integration_accounts`, `delivery_jobs`, `integration_events`, `audit_log`, `retention_jobs`.
- Во всех объектах: UUID, tenant_id, created_at/updated_at, статус, версия, источник и actor_id; PII помечать отдельным классификатором и ограничивать доступ по полям.

## Как должен работать «конкурентный сбор» КП (10/10 по пользе, но не веб-скрейпинг личных кабинетов)
- В одной сделке брокер создаёт запрос, назначает уполномоченных лизингодателей и отправляет через законный канал (API по договору, официальный email или ручная загрузка).
- Сохранять сам оригинал КП, источник, время получения, версию, срок действия, финансовые условия и список нераспознанных полей.
- OCR/AI только предлагает извлечённые значения; брокер подтверждает их. Не обозначать расчётный пример как реальное предложение.
- Сравнение на одинаковых исходных данных; рядом показывать и неподдающиеся прямому сравнению условия. Каждый итог можно проследить до источника.
- Не обходить CAPTCHA, аутентификацию или ограничения сайтов партнёров; не использовать роботов для неразрешённого доступа.

## Compass Connect: решение
**Нужен, но как инфраструктурный Integration Hub, а не ещё один чат.** Для каждого партнёра: отдельный адаптер, права на данные, версия схемы, лимит запросов, тестовый режим, очередь повторных доставок, подтверждённый статус получения, ручной переключатель включения. MAX — лишь канал уведомления/связи после подтверждения официального профиля и поддерживаемого API; не передавать паспорта/договоры в сообщения по умолчанию. На первом этапе email+ручное КП надёжнее выдуманной автоматической интеграции. Не привязывать бизнес-логику напрямую к одному мессенджеру.

## Обязательные правила защиты
- Проверять права **на сервере для каждого объекта и поля**: broker видит назначенные сделки; supervisor — явно закреплённую команду; admin — настройки, но доступ к ПД отдельно ограничивается; auditor — журнал по разрешению, без автоматического просмотра полных документов.
- MFA, ограничение сессий, CSRF, CSP, rate limits, безопасный upload через карантин/антивирус, аудит без секретов/ПД, разграничение окружений, тест восстановления, процедура удаления.
- Для AI: изоляция инструкций от пользовательских документов, фильтрация prompt injection, журнал решения/модели/версии, запрет самостоятельной отправки КП и отказов без человека. Не использовать конфиденциальные документы для обучения без отдельного разрешения.
- Сбор ПД в РФ — только после проверки применимых требований 152-ФЗ, уведомлений, локализации, договоров с обработчиками, сроков и оснований. Проектная документация не является юридическим заключением.
- Отдельный feature flag на каждый внешний коннектор и приём заявок; **все выключены по умолчанию**.

## Очерёдность внедрения и критерии завершения
1. **Фундамент:** роли, модель доступа, миграции БД, тесты запрета чужих сделок, журнал аудита, настройки секретов, отдельная среда.
2. **Рабочий брокерский MVP:** очередь синтетических заявок, карточка сделки, 2–20 КП, сравнение и ручной экспорт; статус «готово» только после браузерных/интеграционных тестов.
3. **Разрешённый приём:** правовые документы/хостинг/операторская очередь/согласие/антиспам; только после явного согласования.
4. **Инструменты эксперта:** Verify, Document, Legal, Analytics; измерять долю извлечений, подтверждённых человеком.
5. **Источники и AI:** Market, Radar, Subsidy, Vision, Intelligence, Connect; проверка лицензий, качества и стоимости запросов.
6. **Публичный релиз/SEO:** независимая проверка SEO Engine, редакторское одобрение, DNS/HTTPS, robots/sitemap, аналитика и затем отдельная команда на индексацию.

### Приёмочные тесты
- Клиентский/брокерский запрос без авторизации -> 401; чужая сделка -> 403/404 без утечек; разрешённая сделка -> 200 с полевым маскированием.
- Два одновременных изменения одной версии -> контроль конфликта; два одинаковых события интеграции -> один результат.
- Все КП с реальным источником; даты/комиссии/выкуп не теряются; AI-ошибка не превращается в утверждённые цифры.
- Документ содержит вредоносный payload -> карантин/отказ; внешние AI и интеграции отключены -> предсказуемый результат, без подставного «успеха».
- Публичная ссылка V5 не меняется, preview noindex, формы не отправляют ПД, GitHub Pages не содержит секретов.
